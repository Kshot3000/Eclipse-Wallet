Build on Eclipse

Eclipse injects a minimal, approval-first provider — window.eclipse — on every http(s) page. Three chains, one object, no SDK, no backend. This is the complete integration reference.

Introduction

Eclipse is an all-in-one, self-custody browser wallet for Cardano (ADA), Midnight (NIGHT) and Bitcoin (BTC), running on Chrome and Brave. For developers it exposes the same kind of provider object as Phantom, MetaMask or Eternl:

window.eclipse // the provider (alias: window.EclipseWallet) window.eclipse.isEclipse // true window.eclipse.name // 'EclipseWallet' window.eclipse.version // '0.1.0' window.eclipse.chains // ['cardano', 'midnight', 'bitcoin']
Approval-first by design. Every method resolves only after the user approves the request in the wallet (or after it times out). Nothing runs silently, and the provider never exposes keys, raw transactions or any wallet internals.

Scope of v0.1: address retrieval and message signing on all three chains. On-chain transaction building (CIP-30-style) is on the roadmap.

Detecting Eclipse

The content script injects window.eclipse on every http:/https: page before your scripts run, and is a no-op if the object already exists. Feature-detect before you call anything — never assume the wallet is installed:

if (window.eclipse) { // Detection is synchronous — no wallet round-trip happens yet. // (Signing later requires the wallet to be unlocked.) const ok = window.eclipse.isEclipse; // true const chains = window.eclipse.chains; // ['cardano','midnight','bitcoin'] } else { // Show "install Eclipse" guidance instead of failing. }
Don't block page load on the wallet. Detection is synchronous and cheap; the wallet-specific UI should appear on user action (a "Connect with Eclipse" button), not automatically on page load.

Requesting an address

getAddress(chain) → Promise<{ address, chain, network }>

Asks the user for the wallet's address on the given chain. The address always matches the network the user has selected for that chain in Eclipse settings:

getAddress
// One-liner: const { address, chain, network } = await window.eclipse.getAddress('cardano'); // Typical dApp flow: if (network === 'mainnet') { showAddress('Receive ADA to:', address); // addr1… }

The wallet validates that any address it later signs with matches the selected network — a dApp cannot trick a user into cross-network approvals.

Signing messages

signMessage(chain, message) → Promise<{ chain, scheme, signature, pubKey, address }>

Signs an arbitrary UTF-8 message with the wallet's key for that chain. Each chain uses its native, spec-verified signing scheme — no wallet-specific envelope:

const sig = await window.eclipse.signMessage( 'bitcoin', 'Hello from my dApp!' ); // sig === { chain: 'bitcoin', scheme: 'ecdsa-secp256k1-sha256', signature: '<base64, 64 bytes>', pubKey: '<hex, 33-byte compressed key>', address: 'bc1…' }
ChainschemeSigned overSignaturepubKey
'cardano'ed25519 raw UTF-8 message bytes 64-byte Ed25519 (base64) 32-byte raw public key (hex)
'midnight'bip340-schnorr raw UTF-8 message bytes 64-byte BIP340 Schnorr (base64) 32-byte x-only key (hex)
'bitcoin'ecdsa-secp256k1-sha256 SHA-256(message) 64-byte compact r‖s, low-S (base64) 33-byte compressed key (hex)
Verifying off-chain. All three schemes are standard and verifiable with any library: Ed25519 (RFC 8032), BIP340 (Schnorr over the raw message), and secp256k1 ECDSA over SHA-256(message). The scheme field tells you exactly which check to run — branch on it, never on the chain string alone.

Message limit: 100,000 characters. Signing requires the wallet to be unlocked — if the user approves while locked, you receive the Wallet is locked — unlock first error and can ask them to try again.

The request() API

request(args) → Promise<result>

The generic form — the same call every convenience wrapper makes. Use it when you prefer a single, future-proof entry point:

Errors & timeouts

Every rejection is an Error whose message is a stable, documented string. Two of them are user decisions — treat them as normal flow, not failures. The rest are transport or state problems:

// Reference error handling: try { const { address } = await window.eclipse.getAddress('cardano'); showAddress(address); } catch (e) { if (e.message === 'Rejected by user' || e.message === 'Request timed out') { showHint('No problem — you can connect again anytime.'); } else if (e.message.startsWith('Eclipse Wallet')) { showInstall(); } else { throw e; // unexpected — surface it } }

Request lifecycle

What happens between your await and the resolved result — and what the user sees:

1
You call getAddress() / signMessage(). The content script forwards it to the wallet's background broker with your page's origin.
2
The wallet queues it. The toolbar badge increments. If the popup is closed, a desktop notification is shown: "… wants your cardano address. Open Eclipse Wallet to approve."
3
The user decides. In the dApps tab they see your origin, the chain, the exact message (for signing) and — optionally — a Remember checkbox so that origin isn't asked again for that chain.
4
The result comes back — or the request expires after 5 minutes. The queue survives browser/worker restarts, so a pending request is never silently lost.
Remembered origins are listed in the dApps tab and can be removed at any time. Remembered origins still show up in the queue — they approve faster, but the user always sees what's happening.

Best practices

🔍

Detect first

Always branch on if (window.eclipse). A dApp that works without the wallet is a dApp that works for everyone.

👆

Act on intent

Request the address when the user clicks something — never on page load. That's the single biggest trust signal in web3 UX.

🧾

Show before you sign

Render the exact message text in your UI so the user can confirm it matches what the wallet shows. Signing a surprise is the #1 phishing vector.

🚸

Handle rejection kindly

Rejected by user and Request timed out are decisions, not errors. No retry loops, no dark patterns — offer a clear "try again".

🔐

Treat results as sensitive

Signatures and addresses are personal data. Don't console.log them, don't ship them to a backend the user didn't ask for.

🌐

Respect the network

The network field in getAddress() is the user's choice. If your dApp is mainnet-only, say so and don't use testnet addresses.

Security model

What the provider exposes — and what it structurally cannot:

✅

Exposed

Public addresses, message signatures, chain ids, network ids, wallet name and version. All of it is public-key material.

🚫

Never exposed

Private keys, seeds, balances, transaction history, raw transaction bytes. v0.1 has no transaction-signing surface at all.

🛡️

Broker is keyless

The background service worker that relays your requests has no access to key material. Signing happens in the unlocked popup page — a page it cannot read from.

👁️

Nothing silent

Every request is visible: badge, notification, queue entry with origin + chain + message. Approval is per-request; remembering an origin is the user's explicit choice.

Full details in the security section of the main site and in the repository's README.md.

Build from source

Eclipse is a single Manifest-V3 codebase — the same folder loads on Chrome and on Brave. No build step, no npm install, no credentials: every dependency is vendored in-repo.

# Clone git clone https://github.com/Kshot3000/eclipse-wallet cd eclipse-wallet # Verify (Node 22+, fully offline — 176 checks) node tests/run_tests.mjs # 113 unit checks vs. official spec vectors node tests/smoke_extension.mjs # 63 offline integration checks # Load the extension # → chrome://extensions (or brave://extensions) # → Developer mode → "Load unpacked" → select extension/

Test coverage includes BIP39, SLIP-0010, RFC 8032 Ed25519, BIP143 + byte-exact signed BTC transactions, all 27 BIP340 vectors, Midnight SDK vectors, RFC 8949 CBOR and BLAKE2b KATs — every signature independently verified against the spec.
